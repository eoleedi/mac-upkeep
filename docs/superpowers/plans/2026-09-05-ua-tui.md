# UA TUI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and install a configurable Go TUI that runs update commands with bounded concurrency, shows each command's status, and exposes complete live logs in a split pane.

**Architecture:** A TOML loader produces validated task definitions, a runner owns queueing and subprocess lifecycle through an event stream, and a Bubble Tea model owns all display state. The command entry point wires those units together, reports aggregate exit status, and keeps shell migration separate until harmless smoke checks pass.

**Tech Stack:** Go 1.27, Bubble Tea, Bubbles viewport, Lip Gloss, BurntSushi TOML, Go standard library process groups and signals

**Spec:** `docs/superpowers/specs/2026-09-05-ua-tui-design.md`

## Global Constraints

- Source lives in `~/GitHub/ua`; the binary installs to `~/.local/bin/ua`; the default config path is `~/.config/ua/config.toml`.
- Commands start immediately and execute in configuration order with configurable concurrency defaulting to exactly `3`.
- Commands execute through `/bin/zsh -lc`, inherit the caller environment and working directory, and run in separate process groups.
- Enabled task states are exactly `queued`, `running`, `succeeded`, `failed`, `canceled`, and `unavailable`.
- A task failure must not stop unrelated tasks; retries are available only for failed and canceled tasks.
- Complete logs live only in process memory for the current TUI session.
- Confirmed cancellation sends `SIGTERM`, waits two seconds, then sends `SIGKILL` to surviving process groups.
- The final exit status is zero only when every enabled task's latest result is successful.
- Do not remove the existing Zsh alias or functions until automated tests, vet, and the harmless smoke run pass.

- [ ] **Step 3: Implement the event-loop scheduler**

Implement `Manager` with a private command channel and one coordinator goroutine. Only that goroutine mutates task states, queue contents, active count, and retry eligibility. Worker goroutines send completion commands back to the coordinator. Use a buffered public event channel and an `eventWriter` that emits `Event{TaskID: id, Output: string(p), At: now}`.

At startup:

1. Filter disabled tasks before constructing `runner.Task` values in `cmd/ua`.
2. Check every requirement with `LookupFunc`.
3. Emit `Unavailable` for a task with a missing requirement; otherwise emit `Queued` and enqueue it.
4. Start tasks in list order until the active count reaches the limit.

On completion, map `Result` to `Succeeded`, `Failed`, or `Canceled`, emit the terminal event, decrement active count, and fill the free slot. Keep the public event channel open after all tasks finish so a later retry can emit more events. Close it only after `Cancel` has drained workers; close an internal `done` channel for `Wait` at the same point.
